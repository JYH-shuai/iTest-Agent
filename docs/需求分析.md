# iTest-Agent 需求分析说明书

> 版本：v1.0  
> 日期：2026-08-11  
> 作者：金赟浩  
> 项目定位：基于 LangGraph 多 Agent 协作的智能测试用例自动生成与执行系统  
> 对应简历项目：iTest-Agent：基于多 Agent 协作的智能测试用例自动生成系统

---

## 1. 项目背景与目标

### 1.1 背景

传统软件测试中，测试用例编写依赖人工逐条设计，存在以下痛点：

| 痛点 | 现状 | 后果 |
|------|------|------|
| 用例编写耗时 | 手工逐条编写，覆盖度依赖个人经验 | 需求量大时人力成本高、上线周期被拉长 |
| 需求变更响应慢 | 需求变更后手工排查受影响用例 | 用例与需求脱节，回归漏测风险高 |
| 用例不可追溯 | 不清楚每条用例对应哪条需求 | 评审、验收、缺陷定位困难 |
| 执行效率低 | 手工执行或脚本分散在各工具中 | 执行结果无法统一汇总、无法自动生成报告 |

### 1.2 项目目标

建设一套 **输入 PRD（产品需求文档）→ 自动需求分析 → 自动生成测试用例 → 自动执行 → 自动输出测试报告** 的多 Agent 协作系统，用于：

1. 降低测试用例设计与维护成本；
2. 提升用例对需求的覆盖度与可追溯性；
3. 通过 MCP 协议对接真实测试工具（浏览器 UI 测试、接口测试），实现“生成即可执行”；
4. 需求变更时支持增量更新，只重生成受影响用例。

### 1.3 成功标准（量化）

| 指标 | 目标值 |
|------|--------|
| 功能点提取 | 单份 PRD 提取功能点 ≥ 5 个，人工评估准确率 ≥ 80% |
| 用例覆盖 | 每个功能点生成 ≥ 3 条用例，覆盖正常 / 边界 / 异常场景 |
| 用例评审通过率 | 首轮评审通过 ≥ 70 分（满分 100） |
| 双向追溯 | 100% 用例可追溯到需求原文段落；需求点可反向查到所有关联用例 |
| 执行成功率 | 工具环境就绪时单条用例执行成功率 ≥ 90%（含重试） |
| 端到端时效 | 单份 PRD 全流程（分析→生成→评审→执行→报告）≤ 30 分钟 |
| 部署 | Docker Compose 一键启动全部服务（Agent + 向量库 + 执行环境） |

## 4. 需求范围

### 4.1 范围内（本次交付）

1. PRD 需求分析：解析 Markdown PRD，提取功能树（一级功能 → 二级子功能）、优先级、验收标准、测试建议，并给出需求原文引用。
2. 测试用例生成：基于测试方法论 RAG 知识库与历史用例库，生成结构化用例（步骤、预期、前置条件、类型、优先级、追溯信息）。
3. 用例评审：自动检查覆盖度、边界/异常场景、步骤完整性、前置条件，输出评分；不通过自动回退重新生成（带重试上限）。
4. 用例执行：通过 MCP 协议调用 Playwright MCP Server（UI 测试）与 API Test MCP Server（接口测试）真实执行；环境不可用时降级为模拟执行。
5. 测试报告：汇总需求概览、用例统计、评审结论、执行结果、缺陷聚类，输出 Markdown / PDF / JSON / Excel。
6. 双向追溯矩阵：每条用例关联需求原文段落；需求变更自动定位受影响用例。
7. 增量更新：需求变更时仅重生成变更功能对应用例，其余继承。
8. FastAPI 服务层：提供 PRD 上传、全流程/增量执行、任务状态查询、报告下载等 REST 接口。
9. MCP Server（自研）：
   - Playwright MCP Server：封装浏览器导航、点击、填表、截图、文本校验等工具；
   - API Test MCP Server：封装 HTTP 请求发送、响应状态/字段断言等工具。
10. 容器化部署：Docker Compose 一键启动 Agent 服务 + Chroma 向量库 + 执行环境。

### 4.2 范围外（后续迭代）

- 多项目/多用户并发调度与权限体系；
- PDF / Word PRD 解析（当前仅 Markdown，接口预留）；
- 分布式向量库（Milvus）迁移；
- 与缺陷管理系统（Jira/禅道）对接；
- 基于 LLM 的用例质量评估（LLM-as-a-Judge）深度集成。

## 7. 系统架构与 Agent 设计

### 7.1 总体架构

```
┌──────────────────────────────────────────────────────────────┐
│                       FastAPI 服务层                          │
│  POST /pipeline · GET /tasks/{id} · GET /tasks/{id}/report    │
└──────────────────────────┬───────────────────────────────────┘
                           │
┌──────────────────────────▼───────────────────────────────────┐
│                  LangGraph StateGraph 工作流                  │
│                                                              │
│  需求分析Agent → 用例生成Agent → 用例评审Agent ─(不通过)─→ 重新生成 │
│       │              │              │                        │
│       │              │              │ (通过)                 │
│       │              │              ▼                        │
│       │              │         执行Agent ──→ 报告Agent ──→ END│
│       └──────────────┴──────────────┘                        │
└────────────┬───────────────────┬──────────────┬──────────────┘
             │                   │              │
     ┌───────▼───────┐   ┌───────▼──────┐  ┌────▼─────────────┐
     │ RAG 知识库     │   │ MCP 工具层    │  │ 持久化           │
     │ Chroma        │   │ Playwright   │  │ SQLite Checkpoint│
     │ + 方法论/用例库 │   │ API Test     │  │ JSON 产物        │
     └───────────────┘   └──────────────┘  └──────────────────┘
```

### 7.2 Agent 职责

| Agent | 输入 | 输出 | 关键技术 |
|-------|------|------|----------|
| 需求分析 Agent | PRD 文档 | 功能树 JSON（含引用） | LLM + Prompt 模板 + RAG |
| 用例生成 Agent | 功能树 | 标准化 TestSuite | 骨架映射 + LLM 填充 + 知识库参考 |
| 用例评审 Agent | 用例集 | 评审结果（分数/缺口） | 规则引擎（非 LLM，确定性可复现） |
| 执行 Agent | 用例集 | 执行结果 + 日志 | MCP 工具调用 + 重试 + 降级 |
| 报告 Agent | 各阶段产物 | Markdown/PDF/JSON/Excel | 模板渲染 + 统计聚类 |

### 7.3 工作流状态机

```
init ─→ analyze_requirements ─→ generate_testcases ─→ review_testcases
                                                          │
                        ┌─────────────────────────────────┤
                        │ 通过                            │ 不通过（≤ 重试上限）
                        ▼                                 ▼
                  execute_testcases ──→ generate_report ──→ finalize
                        │                                  ▲
                        │ 错误                             │
                        └──────→ handle_error ─────────────┘
```

关键规则：
- 评审不通过自动回退 `generate_testcases`，重试耗尽后进入错误处理；
- 任何节点异常进入 `handle_error`，按错误分类决定重试 / 跳过 / 降级 / 取消；
- 每个节点完成后状态写入 Checkpoint，支持中断恢复。

## 9. 关键业务规则

### 9.1 优先级规则

- P0：核心主流程，不通过则无法上线；
- P1：重要功能，存在替代方案；
- P2：一般功能，可后置。

### 9.2 用例类型推断规则

| 关键词 | 类型 |
|--------|------|
| 性能/并发/压力/负载/吞吐 | 性能测试 |
| 安全/权限/认证/加密/注入/XSS/CSRF | 安全测试 |
| API/接口/调用/HTTP/REST | 接口测试 |
| 兼容/浏览器/平台/设备 | 兼容性测试 |
| 默认 | 功能测试 |

### 9.3 评审规则（确定性规则引擎）

1. 每条用例必须有步骤（steps 非空），缺失扣 30 分/条比例；
2. 每条用例必须有前置条件，缺失扣 10 分/条比例；
3. 存在 P0 功能但无 P0 用例，扣 20 分；
4. 无边界/异常场景用例（>2 条时），扣 10 分；
5. 边界/异常流程用例占比 < 30% 视为覆盖度不达标（硬性门槛），扣 10 分并触发回退补充；
6. 总分 ≥ 70 且覆盖度达标才通过，否则回退重新生成（上限默认 3 轮）。

### 9.4 增量更新规则

- 变更类型：全量更新 / 增量更新 / 新增功能 / 删除功能；
- 增量模式下仅对 `changed_function_ids` 对应的功能重新生成用例；
- 其他功能从历史分析结果继承，保证变更影响面最小。

### 9.5 执行与重试规则

- 每条用例独立执行、独立重试（默认 2 次、指数退避 + 抖动）；
- 执行模式：`mcp`（真实工具）优先，`simulated` 降级；
- 执行结果四态：passed / failed / blocked / skipped。

## 11. 验收标准（Pass / Fail）

| 验收项 | Pass | Fail |
|--------|------|------|
| 需求分析 | 功能点 ≥ 5，准确率 ≥ 80%，含优先级与引用 | 功能点 < 5 或引用缺失 |
| 用例生成 | 每功能点 ≥ 3 条，正常/边界/异常覆盖 | 任一点 < 3 条或类型缺失 |
| 用例评审 | 评分、缺口、回退逻辑正确 | 回退不生效或评分异常 |
| 执行 | MCP 模式可调用真实工具；模拟模式可降级 | 全部失败且无法降级 |
| 报告 | 四要素齐全，多格式可导出 | 缺要素或导出失败 |
| 追溯 | 100% 用例可追溯，矩阵可导出 | 存在孤立用例 |
| API | 四个核心接口可用，任务可轮询 | 接口报错或任务状态不一致 |
| 部署 | Docker Compose 一键启动 | 任一服务启动失败 |

## 12. 风险与应对

| 风险 | 等级 | 应对 |
|------|------|------|
| LLM 生成用例质量不稳定 | 高 | 确定性评审规则把关 + 重试回退 + 人工抽查 |
| Playwright 环境差异导致执行失败 | 中 | Docker 容器化 + 重试 + 超时 + 模拟降级 |
| 向量检索相关性不足 | 中 | 方法论知识库 + 语义检索；后续加 Hybrid/Rerank |
| 本地 Embedding 模型加载慢 | 中 | 模型缓存 + 服务启动预加载 |
| MCP 工具真实执行不可用时影响演示 | 中 | 设计 `simulated` 模式保证流程可跑通 |
